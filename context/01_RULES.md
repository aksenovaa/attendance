# Правила обработки и проверок

## Приоритет источников
Рукописная правка/скан > Workly (лог событий, затем сводная) > реконструкция по паттерну.
Бумага офсета округлена до 0,5 ч: |Δ| ≤ 30 мин → оставляем Workly.

## Аномалии
R1 глюк-пара/дубль ≤5 мин → удалить локально; если приход+уход есть, а отработано 00:00 → пересчитать.
R2 нет ухода/прихода → часы не начислять; ждать скан, иначе реконструкция.
R3 уход «переехал» на утро (≈24:xx) → локально очистить; в Workly чинится вставкой out в реальный конец + поглощение бродячего события.
R4 приход = уход → глюк, удалить локально.
R5 переход через полночь при утреннем старте — норма; смена по дате ПРИХОДА; отработано = уход − приход + 24 ч.
R6 длинные смены ШФ (14–18 ч) — норма.
R7 допуск бумаги ±30 мин.
R8 «бумажные» сотрудники вне табеля без прямого указания.
R9 «24:00» = полночь; синтез табеля по заявленной сумме часов.

## Метки
добавлено | правка | реконструкция. Состояния: Выходной, Отпуск, нет ухода, глюк.
«ночь» — только если смена началась после обеда и закончилась утром.

## Ночная политика (11.11.2026)
Ночные/утренние значения Workly не обнуляем: оставляем как в дампе (Альфредо 19/22/29.10 = 21:13 / 20:56 / 12:19).

## Write-back (разрешён 11.11.2026)
- Только после утверждения месяца; --dry-run по умолчанию, --confirm для отправки.
- Модель: пары событий. Любое лишнее событие «поглощается» парой в 1 секунду.
- Синтез R9 пушить РАЗРЕШЕНО, но последним, после финального утверждения суммы.
- Ledger обязателен + копия на Диск: в Workly и синтез, и ручные правки имеют mode=manual.
- Откат: удаление событий в веб-UI по списку из ledger (подтверждено 11.11.2026).
Повторный push — только через планировщик, без дублей.

## Проверки (любой FAIL → стоп + таблица расхождений)
П1 Σ строк = итог Workly (допуск = число рабочих строк); дней = дни месяца; состав = ростер (без админа).
П2 каждая рукописная ячейка разложена; low confidence → очередь подтверждения, в итог не входит.
П3 у каждой метки есть источник; старый итог − удалённое + добавленное = новый.
П4 однопарные дни: отработано = уход − приход (+24 ч). Мультипарные (pairs>1):
0 ≤ отработано ≤ (уход − приход), день помечается «мультипара». Нет дублей (сотрудник, день); итоги = Σ строк.
П5 формат: шапка, метки из списка, HH:MM, итоги, пагинация по сотрудникам.

## Запреты
LLM не считает арифметику и не достраивает отсутствующие строки. Нет данных → «нет данных».

## Ретроспектива этапа (обязательно после закрытия каждого большого шага)
После закрытия этапа фиксируем в docs/RETRO.md и кратко в 03_STATUS четыре пункта:
1) что можно улучшить в результате; 2) что можно было сделать лучше по процессу;
3) какие правила ввести; 4) лучшие наработанные практики разработки.
Первое ретро (S1) проведено 12.11.2026.

## Правила процесса (обязательны)
1. reconcile-gate: любой внешний источник сверяется с независимым эталоном до использования.
2. Нормализация причуд вендора — один раз в клиенте, не в коде приложения.
3. Боевые write-операции — сначала на тестовой сущности, затем dry-run + ledger.
4. Факт, меняющий контекст, коммитится вместе с кодом; ADR — в момент решения.
5. Эмпирические константы (пороги, допуски) — в `config/rules.yaml`, зафиксированы тестом.
6. Сторож-тест на поведение вендора: тест, который падает, когда вендор исправит дефект.
7. Каждое изменение модели — с проверяемым предсказанием.
8. Golden-месяцы — два независимых набора (raw для П1, final для П4/П5); не смешивать.
9. Промпты LLM версионируются в 04_PROMPTS.md; любое изменение = фиксация в контексте.
10. Тикет вендору — со сводной таблицей и дампом, не со словесным описанием.

## Обновление контекста (обязательно)
- Файлы контекста ДОПОЛНЯЮТСЯ, а не перезаписываются.
- Новые факты/ADR/статусы — через `cat >> file <<'EOF'`.
- Точечные замены устаревших строк — через `python - <<'PY' ... p.write_text(t)`.
- ЗАПРЕЩЕНО: перезаписывать файл целиком (теряется история, ломается инкремент).
- Экспорт на Диск и коммит — одной строкой: `make context-export && git add -A && git commit ...`.
- Предупреждение «⚠️ КОНТЕКСТ ИЗМЕНИЛСЯ» — только список изменённых файлов.
