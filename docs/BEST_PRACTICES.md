# Лучшие практики проекта attendance (для передачи в схожие проекты)

Этот документ — итог S1 проекта «Арт Полиграфия» (ноябрь 2026).
Содержит правила, выработанные в боевом режиме, с указанием кейса, где они сработали.

## 1. Источники данных и сверка

**Правило 1.1. Любой внешний источник проходит reconcile-gate.**
Перед использованием API-данных сверяем их с независимым эталоном (веб-экспортом/сводной).
Кейс: `t12.work_time` удвоен (322/322 дней) — обнаружено только после сверки с xlsx.
Реализация: `reconcile.py` / `reconcile_events.py`, gate в CI.

**Правило 1.2. Нормализация причуд вендора на границе клиента.**
Если API возвращает странные структуры (PHP-массивы, вложенные dict), нормализуем один раз в клиенте, а не по всему коду.
Кейс: `_meta: []` при пустой выборке, `items` как dict.
Реализация: `WorklyClient.get_all()`.

**Правило 1.3. Raw неизменяем; производные слои перестраиваются.**
Сырые события, сканы, выгрузки — не трогаем. Правки живёт в реестре corrections.
Это даёт воспроизводимость и откат.

## 2. Эксперименты и необратимость

**Правило 2.1. Боевые операции сначала на тестовой сущности.**
Прежде чем пушить в реальных людей — создать «ТЕСТ Табель», воспроизвести кейс, убедиться в модели.
Кейс: write-back проверялся на employee_id 163167 до боевого применения.
Сотрудник удаляется после эксперимента.

**Правило 2.2. Dry-run по умолчанию + ledger для каждой отправки.**
Все write-запросы требуют явного `--confirm`. Каждое отправленное событие пишется в ledger.
Это единственный способ отличить наши правки от чужих (в Workly все `mode=manual`)
и единственный способ сделать откат (DELETE в API нет, откат через веб-UI по списку из ledger).

**Правило 2.3. Проверка модели на реальных данных, а не только на синтетических тестах.**
Кейс: модель пар подтвердилась на 770 днях (0 расхождений), а не только на fixture'ах.

## 3. LLM в контуре разработки

**Правило 3.1. LLM не считает и не достраивает строки.**
LLM — распознавание сканов и оформление решений. Счёт и генерация строк — только в Python.
Это гарантия П4 (арифметика = Σ строк).

**Правило 3.2. Контракт JSON с валидатором.**
Каждый ответ LLM — строго по схеме (scans.json, paper.json, corrections.json).
`confidence: low` → в очередь подтверждения, в итог не попадает без ручного `accept`.

**Правило 3.3. Промпты версионируются в `context/04_PROMPTS.md`.**
Любое изменение поведения распознавания = изменение промпта + фиксация в контексте.

## 4. Процесс

**Правило 4.1. Факт, меняющий контекст, коммитится вместе с кодом.**
Контекст никогда не отстаёт от кода. ADR пишется в момент решения.

**Правило 4.2. Golden-месяцы как регрессия.**
Закрытые месяцы (сентябрь/октябрь 2026) — два набора:
- raw для П1 (raw = raw),
- утверждённый CSV для П4/П5 (финал = финал).
Не смешивать.

**Правило 4.3. Ретроспектива после каждого большого этапа.**
4 пункта в `docs/RETRO.md`: результат / процесс / новые правила / best practices.

**Правило 4.4. Эмпирические константы — в конфиг, а не в код.**
Кейс: предел пары 26 ч, допуск 30 мин для бумаги, допуск 5 мин для глюка — должны быть в `config/rules.yaml`, пинятся тестом.

**Правило 4.5. Тикет вендору — со сводной таблицей, а не со словесным описанием.**
Кейс: письмо v2 с 322-дневной таблицей и CSV-дампом вместо абстрактного «что-то не так».

## 5. Тестируемые предсказания

**Правило 5.1. Каждое изменение модели — с предсказанием.**
Кейс: после удаления 09:50 сводная должна показать 08:00 — это проверяемое условие истинности модели.

**Правило 5.2. Сторож-тест на поведение вендора.**
Если поведение API критично для нас (например, удвоение t12) — пишем тест, который ПАДАЕТ,
когда вендор это исправит. Это наш сигнал вернуться и переключить источник.
